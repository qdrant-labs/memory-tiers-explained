Memory Tiers at 9.5M Points: Search Latency & Resource Efficiency

The same five memory-tier layouts — dense vectors, payloads, payload indexes, and quantized vectors each pinned to cached, cold, or pinned storage — rerun against a ~9.51M-point collection, roughly 1.7× the size of the 5.6M-point run, on the same single Qdrant Cloud cluster. At this scale the two configurations that traded places at 5.6M (Full Cached, With Quantization and Full Cold, No Quantization) shift again, and the Pinned Quantized Vectors configuration now matches the fastest full-precision config on latency outright, at under a third of its memory footprint.

1. What was tested

Each configuration builds the same collection — dense vectors, keyword/int payload indexes on 5 fields — with a different per-component memory tier, then runs the identical 1,677-query search benchmark. On-disk collection size ranges ~48.8–58.7 GB depending on whether quantized vectors are also stored.

Full Cached, No Quantization and Pinned Quantized Vectors are effectively tied at every percentile. Mean latency is 205.5 ms versus 205.4 ms, p50 is 204.7 ms versus 204.7 ms, and both curves stay flat from min to max (3.7× and 3.8× respectively) — the two flattest, most predictable curves of the five. That parity is new at this scale: at 3.8M and 5.6M points the pinned config always paid a latency premium over full-precision caching. At 9.5M it doesn't.
Full Cached, With Quantization partially recovers from its 5.6M collapse, but doesn't fully return to form. At 5.6M its p99 blew up to 7.57 s and max to 13.93 s; at 9.5M those tail numbers shrink back to p99 1,637.7 ms and max 3,383.7 ms — far better, but still 1.5× the mean latency of Full Cached, No Quantization, for a config that stores the same float vectors plus a quantized copy. Its behavior across scales (3.8M fast → 5.6M catastrophic → 9.5M moderate) is non-monotonic, which is itself the finding: this configuration's tail latency doesn't move predictably with dataset size.
Full Cold, No Quantization is still the worst performer by every measure — p50 216.3 ms looks unremarkable, but p95 jumps to 3,742.2 ms, p99 to 9,595.8 ms, and max to 14,516.2 ms, a 67× blowup from median to max. It also improved in absolute terms relative to its own 5.6M numbers (mean dropped from 1,295.8 ms to 733.5 ms) even though the dataset grew — another sign that these tail behaviors don't scale linearly with point count on this cluster.

3. Memory & resource footprint

Qdrant's reported memory total splits into dedicated RAM (memory the process commits and holds, non-evictable — what pinned tiers and index sidecars use) and OS page cache (memory the kernel opportunistically fills with pages the cached tier has touched — reclaimable under system pressure). The dashed tick marks each configuration's on-disk collection size for reference.

Dedicated RAM OS page cache (resident) On-disk collection size (hover for value)
Pinned Quantized Vectors needs only 13.33 GB of guaranteed, non-evictable RAM (15.77 GB total) against a 58.7 GB on-disk size — 3.1× less total memory than Full Cached, No Quantization (49.04 GB), for latency that is now statistically indistinguishable from it.
Full Cached, No Quantization and Full Cached, With Quantization both pull nearly their entire dataset into OS page cache — 48.64 GB and 55.79 GB resident respectively, against on-disk sizes of 48.9 GB and 58.7 GB. Neither configuration's "cached" tier is holding a working set smaller than the collection at this scale; it is holding the whole thing.
"Cold" still drifts back toward "cached" under sustained load. Full Cold, No Quantization started near-empty but pulled 41.38 GB back into OS page cache over the 1,677-query run, 85% of its on-disk size, while still posting the worst tail latency of the five. Full Cold, With Quantization stays much leaner (12.23 GB, 21% of disk) because queries mostly touch the small quantized vectors rather than the full-precision copy.

4. The efficiency frontier

Plotting mean search latency against total memory footprint (dedicated RAM + resident OS cache) puts both axes on one chart. The bottom-left corner is the efficient corner: fast and lean. Mean latency spans 205.5–733.5 ms and footprint spans 12.62–56.19 GB.

Pinned Quantized Vectors is the clear efficient-corner winner: lowest mean latency on the chart (205.4 ms, within 0.08 ms of Full Cached, No Quantization), at 3.1× less memory. Full Cached, No Quantization sits directly above it — essentially the same latency, 33.3 GB more memory. Full Cold, With Quantization is leaner still (12.62 GB) but pays for it with 2.2× the mean latency and a far heavier tail. Full Cold, No Quantization and Full Cached, With Quantization occupy the slow-and/or-heavy region this chart is meant to flag.

5. Recommendation

Best overall

Pinned Quantized Vectors

Matches the fastest configuration on mean, p50, p95, p99, and max latency, at 15.77 GB of fixed, predictable RAM instead of an opportunistic cache that has to hold nearly the entire 58.7 GB collection. Tied for the best throughput (4.9 qps) too.

Equivalent latency, more RAM

Full Cached, No Quantization

Statistically the same latency profile as Pinned Quantized Vectors, but only because the cluster keeps essentially the whole 48.9 GB collection resident in OS page cache (48.64 GB) — memory that has to be sized for the full dataset and grows with it.

Memory-constrained, latency-tolerant

Full Cold, With Quantization

Second-leanest footprint (12.62 GB) with a moderate p95 (1,171.9 ms), though p99/max still reach into multi-second territory (3,982.4 ms / 7,782.2 ms). A reasonable fallback only if pinned memory isn't an option.

Avoid

Full Cold, No Quantization

Worst on every latency percentile (9,595.8 ms p99, 14,516.2 ms max) while its OS cache still balloons to 41.38 GB under load — the worst-of-both-worlds outcome, with no offsetting memory advantage over the cached configurations.

Methodology notes & caveats
  • Search benchmark: 1,677 sequential (non-concurrent) queries per configuration against a ~9.51M-point collection (msmarco_v2.1_doc_segmented_*.parquet), one query at a time — these are single-stream latency numbers, not concurrent-load numbers.
  • Four of the five configurations indexed 9,511,868 points; Full Cold, With Quantization indexed 9,503,676 points (8,192 fewer, <0.1% of the collection). This is a minor confound and unlikely to explain the latency differences observed, which are an order of magnitude larger than the point-count gap.
  • Full Cold, No Quantization reported 21 optimizer segments (start and end) versus 20 for every other configuration; this wasn't controlled for and could contribute marginally to its tail latency.
  • Pinned Quantized Vectors leaves --payload-memory / --payload-index-memory unset (server defaults) while every other configuration explicitly pins payload storage to match its dense-vector tier. Its memory/latency profile is driven primarily by the pinned quantized vectors, but the payload-tier default is a confound this run doesn't isolate.
  • Hardware/CPU/network utilization was not reported by the server for this run ("hardware reporting disabled") — the resource-efficiency comparison here is based on Qdrant's reported memory-tier accounting (RAM, OS page cache, disk), not host-level CPU or I/O metrics.
  • "OS page cache, end of run" is the post-benchmark value from each metrics.txt memory snapshot. Pinned Quantized Vectors showed no change in cached bytes between the start and end of its run; Full Cached, With Quantization, Full Cold, No Quantization, and Full Cold, With Quantization all grew substantially over the course of their runs, consistent with cold-started caches warming up under query load.
  • Rankings continue to shift across scales in ways that aren't monotonic: Full Cached, With Quantization was 3.8M's second-best config, 5.6M's second-worst, and 9.5M's mid-pack config; Full Cold, No Quantization got relatively less bad from 5.6M to 9.5M despite the larger dataset. Readers comparing across reports/3.8M, reports/5.6M, and this report should treat each as a snapshot at its own scale rather than assuming a fixed ranking or a monotonic trend holds as data volume grows.
