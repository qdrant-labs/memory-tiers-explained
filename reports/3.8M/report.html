Memory Tiers at 3.8M Points: Search Latency & Resource Efficiency

Five memory-tier layouts from scripts/cloud/ — dense vectors, payloads, payload indexes, and quantized vectors each pinned to cached, cold, or pinned storage — benchmarked against the same ~3.75M-point collection on a single Qdrant Cloud cluster. This report compares their search-latency profile and their memory footprint to find the best latency-per-gigabyte trade-off.

1. What was tested

Each configuration builds the same collection — dense vectors, keyword/int payload indexes on 5 fields — with a different per-component memory tier, then runs the identical 1,677-query search benchmark.

2. Search latency

Latency across the percentile spread — where a config sits at p50 shows typical-case speed; where it sits at p99/max shows how badly a tail query can stall. Y-axis is log-scaled to fit the ~30× range between the fastest median and the slowest outlier on one chart.

Full Cached, No QuantizationFull Cached, With QuantizationFull Cold, No QuantizationFull Cold, With QuantizationPinned Quantized Vectors
Pinned Quantized Vectors has the flattest, tightest curve of the five: p50 204.8 ms and p99 236.0 ms are only 15% apart. Every other configuration's tail is at least 2–17× its own median.
Full Cold, No Quantization has the widest spread: p50 211.4 ms looks competitive, but p95 jumps to 1.54 s and p99 to 3.93 s (max 5.53 s) — an 18× blowup from median to p99, the signature of cache misses falling through to disk on the full-size float vectors.
Quantization's effect on the tail depends on the storage tier it's paired with. On cold storage it tightens the tail sharply: p99 falls from 3.93 s to 1.66 s (2.4×) and max from 5.53 s to 3.69 s, because HNSW scoring hits the much smaller quantized vectors instead of striking cold disk-backed float vectors on every candidate. On cached storage — where the float vectors were already fully resident and fast — adding quantization instead widens the tail (p99 326.9 ms→737.5 ms, max 902.7 ms→1.70 s), likely the added rescoring/decompression step showing up once the cheap cache hit is no longer the bottleneck. Quantization helps most exactly where the uncompressed path was already the slow one.

3. Memory & resource footprint

Qdrant's reported memory total splits into dedicated RAM (memory the process commits and holds, non-evictable — what pinned tiers and index sidecars use) and OS page cache (memory the kernel opportunistically fills with pages the cached tier has touched — reclaimable under system pressure). The dashed tick marks each configuration's on-disk collection size for reference.

Dedicated RAM OS page cache (resident) On-disk collection size (hover for value)
"Cached" is not free. To hit its latency numbers, Full Cached, With Quantization needs ~22.8 GB of the dataset's ~23.2 GB resident in OS page cache — essentially the whole collection warmed into system memory that the instance must have spare, and that the kernel can evict under pressure from other workloads.
Pinned Quantized Vectors needs only ~5.26 GB of guaranteed, non-evictable RAM (the pinned quantized vectors plus payload-index sidecars) to reach its latency numbers — 3.7× less total memory than the cached-with-quantization config, for a faster and far more consistent result.
"Cold" drifts back toward "cached" under sustained load. Full Cold, No Quantization started the run with only ~961 MB cached, but 1,677 sequential queries over the full-precision float vectors pulled ~16.3 GB back into the OS page cache by the end — most of the same memory pressure as the cached tier, plus the worse tail latency along the way. Cold-with-quantization stays much leaner (4.83 GB final) because queries mostly touch the small quantized vectors, not the cold float ones.

4. The efficiency frontier

Plotting mean search latency against total memory footprint (dedicated RAM + resident OS cache) puts both axes on one chart. The bottom-left corner is the efficient corner: fast and lean.

Pinned Quantized Vectors sits alone in the efficient corner — lowest mean latency (206.2 ms) at close to the lowest total footprint (6.23 GB). The two cached configs match or beat it on mean latency only by carrying 3–4× the memory. The two cold configs undercut it on footprint (cold-with-quant: 4.99 GB) but pay for it in mean latency and, more importantly, in tail latency (section 2).

5. Recommendation

Best overall

Pinned Quantized Vectors

Best latency at every percentile, best throughput (4.8 qps), and the most predictable tail — at a fixed, modest RAM cost (~5.3 GB) instead of an opportunistic near-full-dataset cache. The clear choice when search latency and its consistency matter and ~5 GB of guaranteed RAM per ~3.8M points is affordable.

If RAM is abundant & free

Full Cached, With Quantization

Second-best mean/p50 latency, but only by keeping ~23 GB of the dataset resident in OS cache — reclaimable memory that must be sized for the whole collection, and a bigger disk footprint (quantized vectors stored alongside full vectors).

Memory-constrained, latency-tolerant

Full Cold, With Quantization

Leanest steady-state footprint of the quantized configs (4.99 GB) with a moderate tail (p99 1.66 s). A reasonable fallback when RAM is scarce and occasional multi-hundred-ms to low-second stalls are acceptable.

Avoid

Full Cold, No Quantization

Worst on every latency measure (p99 3.93 s, max 5.53 s) and its OS-cache footprint balloons back up to 16.3 GB under sustained querying anyway — the worst of both worlds once the workload runs long enough to warm the cache.

Methodology notes & caveats
  • Search benchmark: 1,677 sequential (non-concurrent) queries per configuration against the same 3,750,897-point collection (msmarco_v2.1_doc_segmented_*.parquet), one query at a time — these are single-stream latency numbers, not concurrent-load numbers.
  • Pinned Quantized Vectors leaves --payload-memory / --payload-index-memory unset (server defaults) while every other configuration explicitly pins payload storage to match its dense-vector tier. Its memory/latency advantage is driven by the pinned quantized vectors, but the payload-tier default is a confound this run doesn't isolate.
  • Upload-time logs for Full Cached, No Quantization and Full Cached, With Quantization only captured the second of two upload invocations (1,990,717 of 3,750,897 points) — their total ingestion time isn't directly comparable to the cold configs, whose logs captured both halves. This report only uses their metrics.txt (search) data, which reflects the full, completed collection.
  • Hardware/CPU/network utilization was not reported by the server for this run ("hardware reporting disabled") — the resource-efficiency comparison here is therefore based on Qdrant's reported memory-tier accounting (RAM, OS page cache, disk), not host-level CPU or I/O metrics.
  • "OS page cache, end of run" is the second (post-benchmark) value from each metrics.txt memory snapshot; it reflects cache state after the full 1,677-query run, not a steady-state average.
