What changed

Only crates/collection-setup/src/setup.rs changed, and only for collections with quantized: true. Everything else — dataset, tier layout, HNSW config, payload indexes, query set — is identical to the earlier results/1.8M/ run.

- ScalarQuantizationBuilder::default().r#type(QuantizationType::Int8.into()) + TurboQuantizationBuilder::default().bits(TurboQuantBitSize::Bits4)

That's an 8-bit-per-dimension scheme swapped for a 4-bit one. Only the two presets that quantize anything were rerun — Cached + quant and Cold + quant from the original five. The other three presets (Cached, Cold, both unquantized) don't touch this code path and weren't rerun.

Disk footprint — the anomaly, revisited

The earlier 1.8M report flagged that combining inline HNSW storage with quantization inflates the on-disk HNSW graph roughly 470× (346MB → 162GB) versus every other preset. TurboQuant doesn't remove that effect, but it roughly halves it.

Reading the disk numbers

On the Cached tier the difference is small either way (10.9GB vs 10.1GB) — inline storage isn't in play there, so this is just the raw size of int8 vs 4-bit quantized vectors.

On the Cold tier — where inline HNSW storage combines with quantization — TurboQuant cuts total disk from 172.9GB to 95.6GB (index disk specifically: 162.3GB → 85.9GB). That's a ~44% reduction, roughly tracking the halved quantized-vector bit width, but the underlying inline-storage + quantization interaction that causes the blow-up in the first place is still there.

⚠ Still worth verifying before the cloud-scale run

TurboQuant halves the damage but Cold + quant still uses ~9× the disk of every non-inline-storage preset for the same 1.76M points. If this scales linearly, disk sizing for a cloud cluster running this preset needs to budget for that multiplier — it doesn't go away with the quantization switch, it's just smaller.

Takeaways

  • TurboQuant wins on every search metric tested, in both tiers. Cached + quant: +67% throughput (99.2→165.4 qps), p99 down 77% (121.8→28.3ms). Cold + quant: +122% throughput (21.5→47.7 qps), max latency down 87% (9.0s→1.19s). No metric got worse.
  • The quantized vectors are almost exactly half the size — 1.81GB → 0.92GB per collection, consistent with the 8-bit→4-bit change. Vector IO read during search roughly halved too (Cached: 31.9→16.4GB; Cold: 10MB→5MB), so less has to move through the page cache to answer the same queries.
  • Upload cost moved in opposite directions per tier — 13% slower on Cached (729.2s→821.9s) but 20% faster on Cold (798.5s→634.9s). Only one run per config exists, so treat this as a lead to confirm with a repeat run rather than a settled result.
  • The inline-storage + quantization disk anomaly survives the switch, just smaller. Cold + quant disk footprint drops from 172.9GB to 95.6GB, but that's still ~9× every non-inline-storage preset for the same data. TurboQuant makes the problem more affordable, it doesn't fix its root cause.

For the cloud-scale run

  • Prefer TurboQuant over scalar for any cold-tier + inline-HNSW preset. It's strictly better on latency, throughput, and disk in this data — there's no tradeoff visible here to weigh against it.
  • Re-run the upload-time comparison once before trusting the cached/cold split — a 13%-slower vs. 20%-faster result from a single run each is exactly the kind of thing that turns out to be noise.
  • Keep budgeting disk for the inline-storage + quantization multiplier even with TurboQuant — 95.6GB for 1.76M points is still roughly 9× the non-inline-storage presets, and that ratio is what should inform cloud disk sizing, not the absolute GB figure from this run.
