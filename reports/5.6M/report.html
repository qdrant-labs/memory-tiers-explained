Memory Tiers at 5.6M Points: Search Latency & Resource Efficiency

The same five memory-tier layouts from scripts/cloud/ — dense vectors, payloads, payload indexes, and quantized vectors each pinned to cached, cold, or pinned storage — rerun against a ~5.65M-point collection, roughly 1.5× the size of the earlier 3.8M-point run, on the same single Qdrant Cloud cluster. At this larger scale one configuration's behavior changes sharply, reshuffling the earlier ranking.

1. What was tested

Each configuration builds the same collection — dense vectors, keyword/int payload indexes on 5 fields — with a different per-component memory tier, then runs the identical 1,677-query search benchmark. On-disk collection size ranges ~29–35 GB depending on whether quantized vectors are also stored.

2. Search latency

Latency across the percentile spread — where a config sits at p50 shows typical-case speed; where it sits at p95/p99/max shows how badly a tail query can stall. Y-axis is log-scaled to fit the ~150× range between the fastest min and the slowest outlier on one chart — nearly 5× wider than the 3.8M run's range.

Full Cached, With Quantization flips from a top-2 finisher at 3.8M to a near-worst one at 5.6M. At 3.8M points it had the second-best mean latency (247.7 ms); at 5.6M its p99 balloons to 7.57 s and max to 13.93 s (mean 635.6 ms) — worse than every configuration except full-cold-no-quantization. Its on-disk footprint (35.0 GB: float vectors + quantized copy) is now the largest of the five, and the "cached" tier apparently can no longer keep the full working set resident without contention — the same failure mode that hurt Full Cold, No Quantization at the smaller scale now also hits the cached-plus-quantization config once the combined dataset crosses whatever cache budget this cluster has.
Full Cold, No Quantization remains the worst performer by a wide margin: p50 301.2 ms looks unremarkable, but p95 already jumps to 7.44 s, p99 to 18.74 s, and max to 26.93 s — an ~89× blowup from median to p99. Cold float vectors with no quantization still means every cache-miss candidate strikes disk directly, and at 5.6M points there are enough of those misses to make this the slowest config on every tail measure.
Pinned Quantized Vectors again has the flattest, most predictable curve: p50 231.1 ms and p99 566.6 ms are only 2.5× apart, and even its max (1.07 s) stays under one second — the only configuration whose tail doesn't reach into the multi-second range at this scale.

3. Memory & resource footprint

Qdrant's reported memory total splits into dedicated RAM (memory the process commits and holds, non-evictable — what pinned tiers and index sidecars use) and OS page cache (memory the kernel opportunistically fills with pages the cached tier has touched — reclaimable under system pressure). The dashed tick marks each configuration's on-disk collection size for reference.

Dedicated RAM OS page cache (resident) On-disk collection size (hover for value)
Full Cached, With Quantization now needs the most memory of any configuration to run — ~29.9 GB resident in OS page cache (30.1 GB total) against a 35.0 GB on-disk size — while also posting the worst latency of the quantized configs. Storing both full-precision and quantized vectors under a "cached" tier means the working set the kernel has to keep warm grew with the dataset, and at 5.6M points it looks like this cluster can no longer hold it all without churn, which shows up directly as multi-second tail latency in section 2.
Pinned Quantized Vectors still needs only ~7.9 GB of guaranteed, non-evictable RAM (9.36 GB total) to reach its latency numbers — 3.2× less total memory than the cached-with-quantization config, for latency that is faster at every percentile and an order of magnitude more consistent.
"Cold" still drifts back toward "cached" under sustained load, and it costs more at this scale. Full Cold, No Quantization started near-empty but pulled ~24.6 GB back into OS page cache over the 1,677-query run — essentially the same memory pressure as the fully-cached tier, plus by far the worst tail latency of the five. Cold-with-quantization again stays leaner (7.26 GB final, versus 4.83 GB at 3.8M) because queries mostly touch the small quantized vectors — but its footprint is growing with dataset size too, just more slowly.

4. The efficiency frontier

Plotting mean search latency against total memory footprint (dedicated RAM + resident OS cache) puts both axes on one chart. The bottom-left corner is the efficient corner: fast and lean. Axis ranges are wider than the 3.8M chart — mean latency now spans 205–1,296 ms and footprint spans 7.5–30.1 GB.

Pinned Quantized Vectors sits closest to the efficient corner among configurations that are both fast and lean — second-lowest mean latency (253.0 ms) at close to the lowest total footprint (9.36 GB). Full Cached, No Quantization edges it out on raw mean latency (204.7 ms) but needs 2.8× the memory to do it. The two configurations that combine quantization with a large resident working set — Cached·Quant and, to a lesser extent, Cold·No Quant — are now firmly in the slow-and-expensive quadrant, the opposite of where they'd want to be.

5. Recommendation

Best overall

Pinned Quantized Vectors

Best throughput (4.0 qps) and by far the tightest, most predictable tail (p99 566.6 ms, max under 1.1 s) among configurations that don't require tens of gigabytes of resident cache — at a fixed, modest RAM cost (~7.9 GB) instead of an opportunistic near-full-dataset cache. The safest choice as dataset size keeps growing, since its behavior barely changed between the 3.8M and 5.6M runs.

If RAM is abundant & free

Full Cached, No Quantization

Lowest mean/p50 latency of the five, but requires ~25.9 GB of the dataset resident in OS cache — reclaimable memory that must be sized for the whole collection, and that only grows as the dataset does.

Memory-constrained, latency-tolerant

Full Cold, With Quantization

Leanest steady-state footprint of the quantized configs (7.50 GB) with a moderate p95 (921.9 ms), though its p99/max now reach into the multi-second range (7.99 s / 16.59 s). A reasonable fallback only if RAM is genuinely scarce and occasional multi-second stalls are acceptable.

Avoid

Full Cached, With Quantization & Full Cold, No Quantization

Both now post multi-second p99/max latencies while also carrying large memory footprints (30.1 GB and 24.9 GB respectively) — the worst-of-both-worlds combination that "cached" and "cold, no quantization" avoided at 3.8M but no longer do at 5.6M.

Methodology notes & caveats
  • Search benchmark: 1,677 sequential (non-concurrent) queries per configuration against the same 5,649,026-point collection (msmarco_v2.1_doc_segmented_*.parquet), one query at a time — these are single-stream latency numbers, not concurrent-load numbers.
  • Unlike the 3.8M run, all five configurations' upload.txt logs here captured the complete ingestion (three batch uploads summing to the full 5,649,026 points each), so there is no partial-log confound this time. Total ingestion time ranged from ~2.6 hours (Full Cold, With Quantization) to ~8.6 hours (Full Cold, No Quantization); it is not the focus of this report, which covers steady-state search behavior after ingestion completed.
  • Pinned Quantized Vectors leaves --payload-memory / --payload-index-memory unset (server defaults) while every other configuration explicitly pins payload storage to match its dense-vector tier. Its memory/latency advantage is driven by the pinned quantized vectors, but the payload-tier default is a confound this run doesn't isolate.
  • Hardware/CPU/network utilization was not reported by the server for this run ("hardware reporting disabled") — the resource-efficiency comparison here is therefore based on Qdrant's reported memory-tier accounting (RAM, OS page cache, disk), not host-level CPU or I/O metrics.
  • "OS page cache, end of run" is the post-benchmark value from each metrics.txt memory snapshot; it reflects cache state after the full 1,677-query run, not a steady-state average. For four of the five configurations the pre- and post-benchmark cache values were identical or nearly so; Full Cold, No Quantization and Full Cached, With Quantization showed the largest run-time growth (cache roughly doubling from start to end).
  • This run's per-configuration ranking differs meaningfully from the earlier 3.8M-point run (see reports/3.8M/report.html) — in particular Full Cached, With Quantization was the 3.8M run's second-best mean-latency configuration and is this run's second-worst. Readers comparing the two reports should treat each as a snapshot at its own scale rather than assuming a fixed ranking holds as data volume grows.
